# Как поддерживать знания проекта

## Куда писать информацию

| Ситуация | Место |
| --- | --- |
| Как запустить, проверить или обслужить часть системы | `docs/engineering/` |
| Почему выбрана технология или архитектурный подход | `docs/decisions/` (ADR) |
| Что делает сервис или пакет | `docs/project/` |
| Как тема ложится в учебный план | `docs/learning/` |
| Личный вывод или сложность после практики | сначала `notes/drafts/`, затем `docs/learning-log/` |

## Качество страницы

- Указывай фактические команды и порты, а не предположения.
- Не добавляй secrets, credentials или личные tokens.
- Один источник правды: не копируй одну и ту же инструкцию в README, Notion и несколько Markdown-файлов.
- Если документ описывает изменение кода, обновляй его в той же ветке и проверяй `cd documentation && npm run build`.
- Не создавай страницу для каждой мелочи. Документируй то, что сложно восстановить из кода или нужно повторять.
